## Команда: We Tried

# Техническое задание на разработку программного продукта для планирования встреч

## 1. Общие описание
Необходимо разработать программный продукт для планирования встреч сотрудников внутри компании. Система состоит из клиентского мобильного приложения и серверной части.

## 2. Клиентская часть (Android-приложение)
Клиентом является **Android-приложение**, которое должно быть реализовано на **Kotlin** или **Java** с использованием **адаптивной верстки**.

Приложение должно предоставлять интуитивно понятный интерфейс, в котором реализован следующий функционал:

*   **Регистрация и авторизация** сотрудника.
*   **Настройка личного профиля**.
*   **Создание встречи** с возможностью приглашения других сотрудников. Приглашенные сотрудники должны иметь возможность дать бинарный ответ (**принял** / **не принял**).
*   **Просмотр списка активных приглашений** на встречи с возможностью дать ответ о возможности посещения.
*   **Просмотр собственного расписания встреч** в разрезе дня, недели и месяца.

**Важное условие:** временные слоты для встреч разбиты строго по часам. Например, можно создать встречу на 9:00–10:00, но создание встречи на 9:10, 9:05 и т.д. — невозможно.

## 3. Серверная часть
Сервер представляет собой **микросервис на Spring Boot**, работающий с СУБД **PostgreSQL** или **H2**.

Серверное приложение должно:
*   Предоставлять API, необходимый для полноценной работы мобильного приложения.
*   Осуществлять все основные операции с данными в базе через **Spring Data JPA**.
*   Использовать **Liquibase** для создания схемы базы данных и ее предзаполнения.


## User Stories

*   Я, как новый сотрудник, хочу зарегистрироваться, чтобы получить доступ к корпоративному календарю.

*    Я, как зарегистрированный пользователь, хочу авторизоваться, чтобы мои данные были защищены.

*    Я, как пользователь, хочу редактировать свои ФИО и должность, чтобы коллеги видели актуальную информацию обо мне.

*    Я, как организатор, хочу создать встречу на конкретный час и пригласить коллег, чтобы забронировать их время.

*    Я, как приглашенный, хочу видеть список заявок и давать бинарный ответ (принял/отклонил), чтобы планировать свой день.

*    Я, как активный сотрудник, хочу получать список своих подтвержденных встреч за период, чтобы видеть свою загрузку.

## Use Cases 

**UC-01: Регистрация и аутентификация**

Цель: Обеспечить безопасный доступ к API. Поток:

*    Клиент отправляет POST /api/auth/register с данными пользователя.

*    Бэкенд проверяет уникальность email и хэширует пароль.

*    Для всех защищенных эндпоинтов используется HTTP Basic Auth. Бэкенд извлекает учетные данные из заголовка Authorization.

**UC-02: Создание встречи с валидацией слотов**

Цель: Создать событие в календаре. Предусловия: Организатор авторизован. Основной поток:

*    Организатор передает название, дату, час начала и список ID участников.

*    Бизнес-правило: Бэкенд проверяет, что время начала имеет вид HH:00:00 (минуты и секунды строго нулевые).

*    Создается запись в meetings и записи в invitations (статус PENDING) для всех участников.

**UC-03: Обработка приглашения**

Цель: Изменение статуса участия. Основной поток:

*    Участник запрашивает список своих PENDING приглашений.

*    Участник отправляет PATCH запрос с новым статусом (ACCEPTED / DECLINED).

*    Бэкенд проверяет, что этот invitationId принадлежит именно этому пользователю.

## Список задач для Backend-разработчика

**Модуль 1: Инфраструктура и БД**

*    [] Настройка проекта: Инициализация Spring Boot (Web, JPA, Security, PostgreSQL/H2, Lombok).

*    [] Liquibase Migration (Схема): Создание таблиц:

        users (id, email, password_hash, name, position).

        meetings (id, title, start_at, organizer_id).

        invitations (id, meeting_id, user_id, status).

*    [] Liquibase Migration (Data): Скрипт для создания 3-5 тестовых пользователей для отладки.

**Модуль 2: Модель данных и Безопасность**

*    [] JPA Entities: Реализация сущностей и связей @ManyToOne / @OneToMany.

*    [] Spring Security Config: * Настройка Basic Authentication.

        Доступ к /api/auth/register — permitAll().

        Остальные пути — authenticated().

*    [] DTO Layer: Создание объектов для передачи данных (UserDto, MeetingCreateDto, InvitationDto), чтобы не отдавать наружу хэши паролей.

**Модуль 3: Бизнес-логика**

*    [] User Service: Логика регистрации и обновления профиля.

*    [] Meeting Service: * Валидация "целого часа" (проверка минут через LocalTime.getMinute() == 0).

*    [] Создание записи встречи и автоматическая генерация приглашений.

*    [] Schedule Service: Логика фильтрации встреч по периодам (день/неделя/месяц).

**Модуль 4: API**

*    [] AuthController: Эндпоинт регистрации.

*    [] ProfileController: Эндпоинты получения и PATCH-обновления профиля.

*    [] MeetingController:

        POST /api/meetings — создание.

        GET /api/meetings/schedule — получение списка с фильтрами по дате.

*    [] InvitationController:

        GET /api/invitations — список входящих.

        PATCH /api/invitations/{id} — ответ на приглашение.

**Модуль 5: Качество и Обработка ошибок**

*    [] Global Exception Handler: Обработка 404 Not Found, 400 Bad Request (если время не кратно часу) и 401 Unauthorized.

*    [] Валидация входящих данных: Использование @Valid и javax.validation для проверки email и непустых полей.

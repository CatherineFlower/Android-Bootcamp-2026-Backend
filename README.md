# Техническое задание на разработку программного продукта для планирования встреч

## Команда: Цифровые Экзистенциалисты

## 1. Общие описание
Необходимо разработать программный продукт для планирования встреч сотрудников внутри компании. Система состоит из клиентского мобильного приложения и серверной части.

## 2. Клиентская часть (Android-приложение)
Клиентом является **Android-приложение**, которое должно быть реализовано на **Kotlin** или **Java** с использованием **адаптивной верстки**.

Приложение должно предоставлять интуитивно понятный интерфейс, в котором реализован следующий функционал:

*   **Регистрация и авторизация** сотрудника.
*   **Настройка личного профиля**.
*   **Создание встречи** с возможностью приглашения других сотрудников. Приглашенные сотрудники должны иметь возможность дать бинарный ответ (**принял** / **не принял**).
*   **Просмотр списка активных приглашений** на встречи с возможностью дать ответ о возможности посещения.
*   **Просмотр собственного расписания встреч** в разрезе дня, недели и месяца.

**Важное условие:** временные слоты для встреч разбиты строго по часам. Например, можно создать встречу на 9:00–10:00, но создание встречи на 9:10, 9:05 и т.д. — невозможно.

## 3. Серверная часть
Сервер представляет собой **микросервис на Spring Boot**, работающий с СУБД **PostgreSQL** или **H2**.

Серверное приложение должно:
*   Предоставлять API, необходимый для полноценной работы мобильного приложения.
*   Осуществлять все основные операции с данными в базе через **Spring Data JPA**.
*   Использовать **Liquibase** для создания схемы базы данных и ее предзаполнения.

## User Stories
1. Как сотрудник компании, я хочу зарегистрироваться в системе, чтобы получить доступ к планированию встреч.
2. Как зарегистрированный сотрудник, я хочу авторизоваться в системе, чтобы использовать функционал приложения.
3. Как пользователь, я хочу редактировать свой профиль (имя, должность), чтобы другие сотрудники могли меня корректно идентифицировать.
4. Как организатор встречи, я хочу создавать встречи с указанием даты, времени и списка приглашённых, чтобы планировать совещания.
5. Как приглашённый сотрудник, я хочу просматривать список активных приглашений и давать ответ «принял» или «не принял», чтобы управлять своим участием во встречах.
6. Как пользователь, я хочу просматривать своё расписание встреч по дням, неделям и месяцам, чтобы организовывать рабочее время.

## Use Cases
# UC-01: Регистрация нового сотрудника
**Цель**: Создание учётной записи сотрудника для последующего доступа к системе.

**Участники**: Сотрудник.

**Предусловия**: У пользователя отсутствует учётная запись в системе.

**Основной поток**:
1. Пользователь открывает форму регистрации в мобильном приложении.
2. Вводит email, пароль и имя.
3. Отправляет данные на сервер.
4. Сервер проверяет, что email уникален и пароль соответствует требованиям.
5. Сервер создаёт новую запись в таблице users, сохраняя хэшированный пароль.
6. Сервер возвращает успешный ответ (HTTP 201 Created).

**Альтернативный поток**:
— Email уже зарегистрирован → сервер возвращает ошибку (HTTP 409 Conflict).
— Пароль короче 6 символов → сервер возвращает ошибку (HTTP 400 Bad Request).

# UC-02: Авторизация через HTTP Basic Authentication
**Цель**: Подтверждение личности пользователя при обращении к защищённым endpoint’ам.

**Участники**: Сотрудник, сервер.

**Предусловия**: Учётная запись пользователя существует.

**Основной поток**:
1. Мобильное приложение при каждом запросе к защищённому API добавляет заголовок:
Authorization: Basic base64(email:password).
2. Сервер извлекает и декодирует учётные данные.
3. Проверяет наличие пользователя по email и корректность пароля (сравнение хэшей).
4. Если данные верны — запрос обрабатывается.
5. Если данные неверны — возвращается ошибка.

**Альтернативный поток**:
— Неверные email или пароль → сервер возвращает HTTP 401 Unauthorized.
— Заголовок Authorization отсутствует → сервер возвращает HTTP 401 Unauthorized.

# UC-03: Редактирование личного профиля
**Цель**: Обновление личной информации пользователя.

**Участники**: Сотрудник.

**Предусловия**: Пользователь авторизован (отправляет корректный Basic-заголовок).

**Основной поток**:
1. Пользователь открывает экран профиля.
2. Изменяет имя или должность.
3. Сохраняет изменения.
4. Приложение отправляет PATCH-запрос с новыми данными и заголовком Authorization.
5. Сервер проверяет аутентификацию и обновляет данные текущего пользователя.
6. Сервер возвращает обновлённый профиль.

**Альтернативный поток**:
— Имя не указано → сервер возвращает HTTP 400 Bad Request.
— Попытка изменить чужой профиль → сервер возвращает HTTP 403 Forbidden.

# UC-04: Создание встречи
**Цель**: Запланировать встречу с другими сотрудниками.

**Участники**: Организатор встречи.

**Предусловия**: Пользователь авторизован.

**Основной поток**:
1. Пользователь выбирает дату и время.
2. Указывает название встречи.
3. Выбирает одного или нескольких коллег из списка.
4. Нажимает «Создать».
5. Приложение отправляет данные на сервер с заголовком Authorization.
6. Сервер проверяет, что минуты времени начала равны 0.
7. Сервер создаёт запись в таблице meetings.
8. Для каждого приглашённого создаётся запись в таблице invitations со статусом PENDING.
9. Сервер возвращает подтверждение.

**Альтернативный поток**:
— Не выбраны приглашённые → сервер возвращает HTTP 400 Bad Request.
— Один из указанных пользователей не существует → сервер возвращает HTTP 400 Bad Request.

# UC-05: Ответ на приглашение
**Цель**: Подтвердить или отклонить участие во встрече.

**Участники**: Приглашённый сотрудник.

**Предусловия**: Пользователь авторизован и имеет непрочитанное приглашение.

**Основной поток**:
1. Пользователь просматривает список приглашений.
2. Выбирает встречу и нажимает «Принять» или «Не принять».
3. Приложение отправляет PATCH-запрос с новым статусом (ACCEPTED / DECLINED).
4. Сервер проверяет аутентификацию и обновляет статус соответствующей записи в invitations.
5. Сервер возвращает обновлённый статус.

**Альтернативный поток**:
— Статус уже установлен → сервер возвращает HTTP 400 Bad Request.
— Встреча уже завершилась → сервер возвращает HTTP 400 Bad Request.

# UC-06: Просмотр расписания встреч
**Цель**: Отобразить запланированные встречи в удобном виде.

**Участники**: Пользователь.

**Предусловия**: Пользователь авторизован.

**Основной поток**:
1. Пользователь выбирает период: день, неделя или месяц.
2. Указывает дату.
3. Приложение отправляет GET-запрос с параметрами period и date.
4. Сервер находит все встречи, где пользователь — организатор или приглашённый с подтверждённым статусом.
5. Сервер возвращает список встреч с временем, названием и участниками.
6. Приложение отображает расписание.

**Альтернативный поток**:
— Некорректный период → сервер возвращает HTTP 400 Bad Request.
— Нет встреч в указанный период → сервер возвращает пустой массив.

## Задачи для backend-разработчика
1. **Настроить Spring Boot проект с зависимостями**: Spring Web, Spring Data JPA, Spring Security, PostgreSQL Driver, Liquibase, H2.

2. **Реализовать конфигурацию Spring Security**: разрешить анонимный доступ только к /api/auth/register.

3. **Создать сущности**:
User: id, email (unique), passwordHash, name, position.
Meeting: id, title, startDateTime, organizer (ManyToOne → User).
Invitation: id, meeting (ManyToOne), invitee (ManyToOne), status (enum: PENDING, ACCEPTED, DECLINED).

4. **Написать Liquibase-скрипты**:
Создание таблиц users, meetings, invitations.
Добавление ограничений (UNIQUE на email, внешние ключи).

5. **Реализовать AuthController**:
POST /api/auth/register — регистрация нового пользователя.

6. **Реализовать UserController**:
PATCH /api/profile — обновление имени и должности текущего пользователя.

7. **Реализовать MeetingController**:
POST /api/meetings — создание встречи с валидацией времени.
GET /api/meetings/schedule?period={day|week|month}&date=YYYY-MM-DD — получение расписания.

8. **Реализовать InvitationController**:
GET /api/invitations — получение списка приглашений текущего пользователя.
PATCH /api/invitations/{id}/accept — принять приглашение.
PATCH /api/invitations/{id}/decline — отклонить приглашение.

9. **Реализовать сервисную логику**:
Проверка ownership (пользователь может редактировать только свой профиль, отвечать только на свои приглашения).
Проверка существования приглашённых пользователей при создании встречи.
Настроить глобальный обработчик исключений (@ControllerAdvice) для унифицированного формата ошибок.
